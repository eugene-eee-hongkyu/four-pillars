# A-2. 사주톡 — 프로세스를 화면으로

> **이 문서의 1차 독자는 나 자신이다.**
> Claude와 AI 빌드 도구는 2차 독자.
> 내 생각을 눈으로 보기 위해 Claude의 도움으로 꺼내 쓴 문서다.

---

## 1. A-1 요약 블록

**핵심 가설**
이직·연애·결혼 고민이 있는 28~34세 여성이, 링크로 받은 웹 사주 서비스에서, 긴 해석을 읽은 뒤 스스로 최대 3번의 추가 질문을 써가며 대화를 완주할 것이다.

**Phase 구조**
- P0. 진입 & 재료 수집
- P1. 긴 해석 응답
- P2. 사용자 주도 Q&A 루프 (최대 3회)
- P3. 정리 & 저장 & 조건부 요청

**MVP 경계 3개**

| 항목 | 고정 |
|---|---|
| 제품 | AI 대화형 사주 해석 웹서비스 |
| 타겟 | 28~34세 여성, 수도권, 이직·연애·결혼 고민. Eugene 지인 10명 |
| 목표 행동 | 3번 질문 다 쓰고 정리까지 완주 (보조: 1번 이상 질문 후 완주) |

---

## 2. 화면 목록

- **화면 1. 생시 입력 (S1, 첫 세션만)** — 이름·성별·생년월일·시간 폼
- **화면 2. 고민 입력 (S2)** — 4지선다 카드 (이직·연애·결혼·직접 쓰기)
- **화면 3. 반복 패턴 4지선다 (S3·S4)** — 영역별 맞춤 질문 A/B/C/D
- **화면 4. 대화 화면 (S5~S12)** — 긴 해석 → Q&A 최대 3회 → 정리까지 한 채팅창
- **화면 5. (조건부) 부모 생시/환경 요청 (S13)** — 화면 4 정리 아래 확장. 3번 질문 다 쓴 사용자만

## 4. 화면별 상세 스펙

### 화면 1. 생시 입력 (S1, 첫 세션만)

#### 4-a. ASCII 와이어프레임

```
┌─────────────────────────────────────┐
│ 사주톡                              │
├─────────────────────────────────────┤
│                                     │
│ 반가워요. 먼저 몇 가지만            │
│ 알려주세요.                         │
│                                     │
│ 이름                                │
│ ┌─────────────────────────────────┐ │
│ │                                 │ │
│ └─────────────────────────────────┘ │
│                                     │
│ 성별                                │
│ ○ 여성   ○ 남성                    │
│                                     │
│ 생년월일                            │
│ ┌──────┐ ┌──────┐ ┌──────┐         │
│ │ 년 ▼ │ │ 월 ▼ │ │ 일 ▼ │         │
│ └──────┘ └──────┘ └──────┘         │
│                                     │
│ 태어난 시간                         │
│ ┌──────┐ ┌──────┐                  │
│ │시간 ▼│ │분  ▼│                  │
│ └──────┘ └──────┘                  │
│ □ 시간을 몰라요                     │
│                                     │
│          [ 다음 ]                   │
└─────────────────────────────────────┘
```

#### 4-b. UX 의도

- 이름 필드로 해석 본문·정리에서 사용자를 부르면 체감 상승. 역술가 대면 상담 느낌
- 평달/윤달은 시스템이 만세력 엔진으로 자동 판별. 사용자 노출 시 "윤달이 뭐지" 단계에서 이탈
- "시간을 몰라요" 체크박스는 기억 못 하는 사용자 출구. 체크 시 해석 프롬프트에 "시간 미상" 플래그 전달
- 환영 문구 "몇 가지만 알려주세요"로 회원가입 아님을 암시. 해석 준비 과정으로 프레이밍

#### 4-c. 인터랙션

- 이름 타이핑 → 필드에 글자 표시
- 성별 라디오 탭 → 선택 표시
- 생년월일 드롭다운 각각 탭 → 년(1950~현재)·월(1~12)·일(1~31)
- 시간 드롭다운 탭 → 시간(0~23)·분(0·15·30·45 4단계)
- "시간을 몰라요" 체크 → 시간·분 드롭다운 disabled, 회색 처리
- "다음" 탭 → 필수 필드 검증(이름·성별·생년월일) → 저장 → 만세력 계산 엔진 호출 → 원국 데이터 생성 → 화면 2

#### 4-d. 상태

- 정상: 빈 폼
- 검증 실패: 필수 필드 미입력 시 "다음" 탭하면 해당 필드에 "입력해주세요" 안내
- 로딩: 만세력 계산 중 1~3초, 버튼 disabled + "준비 중..."
- 에러: 만세력 계산 실패 시 "잠시 후 다시 시도해주세요" + 재시도 버튼

#### 4-b. UX 의도

- 4개 카드 = 4지선다 패턴. 화면 3 반복 패턴 질문과 같은 "카드 4개 세로 배치" 구조로 통일. "선택도 하고 입력도 하나?" 혼란 제거
- "직접 쓸게요"가 네 번째 선택지. MVP 타겟 3영역 외 고민도 한 번의 선택으로 진입
- 3개 영역 카드는 탭 즉시 전환, 4번째만 같은 화면에서 확장. 이 차이로 "3개는 바로 진행 / 1개는 한 단계 더"를 직관 전달
- 이름으로 부르기로 대면 상담 느낌 유지

#### 4-c. 인터랙션

- 이직·연애·결혼 카드 탭 → 해당 영역 저장 → 화면 3 자동 전환 (S3 LLM 분류 스킵)
- "직접 쓸게요" 카드 탭 → 카드에 ✓ 표시 + 바로 아래로 텍스트 필드 펼쳐짐 + "다음" 버튼 나타남
- 텍스트 입력 있으면 "다음" 활성
- "직접 쓸게요" 선택 상태에서 다른 카드 탭 → 텍스트 필드 접히고 해당 영역으로 즉시 전환
- "다음" 탭 → 텍스트 저장 → S3 LLM 분류(이직·연애·결혼·기타) → 기타 분류 시 화면 3에서 일반 반복 패턴 4지선다

#### 4-d. 상태

- 정상: 카드 4개 표시, 텍스트 필드 없음
- "직접 쓸게요" 선택: 그 카드 아래 텍스트 필드 펼쳐짐
- 텍스트 입력 중: "다음" 버튼 활성
- 텍스트 빈 상태: "다음" 버튼 disabled
- 로딩: "다음" 탭 후 LLM 분류 1~2초, "읽고 있어요..." 표시

```
│                                     │
│ ┌─────────────────────────────────┐ │
│ │ A. 잘 되다가 갑자기 그만두고    │ │
│ │    싶어짐                       │ │
│ └─────────────────────────────────┘ │
│ ┌─────────────────────────────────┐ │
│ │ B. 처음엔 재미있다가 금방 식음  │ │
│ └─────────────────────────────────┘ │
│ ┌─────────────────────────────────┐ │
│ │ C. 남들은 버티는데 나만 못 버팀 │ │
│ └─────────────────────────────────┘ │
│ ┌─────────────────────────────────┐ │
│ │ D. 잘 모르겠다                  │ │
│ └─────────────────────────────────┘ │
│                                     │
│     (카드 탭 시 바로 진행)          │
└─────────────────────────────────────┘
```

#### 4-b. UX 의도

- "한 가지만 더" 문구로 입력 2단계 거친 사용자 피로 완화. "마지막"임을 명시해 이탈 방지
- 영역별 맞춤 질문 (이직·연애·결혼·기타 각각 다른 질문)
- D "잘 모르겠다" 선택지로 패턴 스스로 몰라도 진행 가능. 이탈 방지 우선
- 카드 탭 = 결정 = 진행. 별도 "다음" 버튼 없음. 탭 수 최소화

#### 4-c. 인터랙션

- 카드 탭 → 선택값 저장 → 화면 4 자동 전환
- 탭 순간 시각 피드백 (눌림 효과)
- 선택 변경은 뒤로가기로만 가능 (카드 탭 시 즉시 전환)

#### 4-d. 상태

- 정상: 4개 카드 표시
- 탭 직후: 시각 피드백 후 즉시 전환
- 로딩: 없음 (선택값 저장 즉시)

## Claude의 적대적 압박 — 이 화면 설계를 죽일 이유 세 가지

**1. 화면 4 대화 화면의 상태 복잡도가 MVP 크기 초과 위험**
한 화면에 6가지 상태(A~F)가 있고, 상태 E는 2회차 + 2번째 질문 + 50% 랜덤 3중 조건. 빌드 도구가 이 상태 전환을 정확히 구현하려면 상태 머신 설계가 필요한데, Lovable 프롬프트 한 번에 되는 범위를 넘어섬. 구현 디버깅에 예상보다 시간 쓸 수 있음.

**2. 화면 5 부모 생시 입력이 대화 맥락과 불일치하는 톤 전환**
화면 4까지는 역술가 톤의 자연스러운 대화였는데, 화면 5 fallback 라디오 4단계 + 환경 Q1·Q2 5단계는 설문조사 느낌. 신뢰 피크 타이밍이라 해도 UI 톤이 급전환되면 "방금 그 역술가 어디 갔어?" 느낌. 라디오 대신 대화형(역술가가 "부모님 두 분 생시 기억나세요?" 말풍선 형식)이 더 일관될 수 있음.

**3. 상태 E 50% 랜덤 삽입의 UX 예측 불가능성**
50% 랜덤은 사용자가 "왜 어떤 때는 나오고 어떤 때는 안 나오지?" 느낄 수 있음. 재방문 사용자가 친구에게 "이렇게 물어봐"라고 설명할 때 재현 안 됨. A/B 테스트 관점에서도 50%는 "의도한 동작"이 아니라 "버그"처럼 보일 위험. 100% 또는 0% 중 하나로 고정이 디버깅·사용자 피드백에 유리할 수 있음.
